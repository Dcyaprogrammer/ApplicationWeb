现在的游戏是处于一个 demo 状态，`gameStore` 里很多流程接近写死。最终产品需要把卡牌放进数据库，并且用一套可控的抽卡算法来维持节奏、难度和教学覆盖。下面先把这一整套系统设计成一个可落地的方案。

# 目标

1. 保留 Reigns 式的随机和重玩价值。
2. 保证留学申请流程中的关键知识点一定会出现。
3. 避免纯随机导致连续高压、数值崩盘、体验不公平。
4. 让后续加卡、改卡、调数值不需要再碰 `gameStore` 硬编码。

# 总体思路

最终系统不应该是“完全随机抽卡”，而应该是：

- 主线里程碑卡 `milestone`
- 阶段内动态事件卡 `dynamic`
- 特殊危机卡 `crisis`
- 恢复/缓冲卡 `recovery`
- 教学解释或知识补充卡 `knowledge`

整体采用“里程碑剧情 + 受控随机事件”的混合模型。

原因：

- 如果完全随机，留学申请里真正重要的知识点可能一局都碰不到。
- 如果完全线性，又会失去 roguelike 的变化和可重玩性。
- 混合模型最适合你们这个“教学 + 叙事 + 类 rogue”项目。

# 和当前代码的映射

目前 `gameStore` 里已经有几种雏形：

- `choice.nextCardId`
  - 对应未来系统里的 `followup` / `forced next`
- `SPECIAL_EVENTS`
  - 对应未来系统里的 `crisis` / `emergency`
- `stats`
  - 对应运行时的显性数值状态

  - 对应时间推进系统
- `requirements`

问题是这些逻辑现在都写在一个 store 里，未来应该拆开：

- `CardRepository`
- `RuleEngine`
- `Director`
- `RunReducer`
- `BalanceConfig`

# 运行时状态设计

建议把一局游戏的状态拆成两层。

## 1. 显性状态

直接影响 UI 或玩家决策：

- `gpa`
- `mentality`
- `energy`
- `experience`
- `money`
- `currentDay`
- `currentPhase`
- `route`

其中 `route` 可以是：

- `agency`
- `diy`
- `mixed`

## 2. 隐性状态

只给系统调度使用，不一定展示给玩家：

- `pressure`
  - 当前整体压力值，决定下一张卡应该偏压迫还是偏恢复
- `flags`
  - 如 `has_ielts`, `essay_submitted`, `interview_failed`
- `seenCards`
  - 本局看过哪些卡
- `cooldowns`
  - 某类卡多久内不能重复出现
- `recentCategories`
  - 避免连续三张同一类卡
- `knowledgeCoverage`
  - 本局已经覆盖了哪些知识点
- `pendingConsequences`
  - 前面选择埋下、后面需要回收的结果

这里最关键的是 `pressure`。  
如果没有这个隐藏指标，系统只能根据四维数值盲抽，很容易连续发高伤卡。

# 卡牌分类设计

建议给每张卡明确 `cardType`。

## 1. `milestone`

关键流程卡，必须推进教学主线，例如：

- 决定找中介还是 DIY
- 语言考试
- 选校
- 推荐信
- 文书
- 面试
- 出结果

特点：

- 必须出现
- 顺序基本可控
- 教学优先级最高

## 2. `dynamic`

阶段内的普通事件卡，例如：

- 同学推荐某中介
- 实验室导师压榨
- 网上刷到经验贴
- 拖延、社交、睡眠问题

特点：

- 用来增加随机性和生活感
- 教学和数值调节兼顾

## 3. `crisis`

高压事件，例如：

- 材料遗漏
- 推荐人失联
- 精神崩溃
- 截止日期逼近

特点：

- 不能连续高频出现
- 需要前兆或条件
- 通常要搭配后续恢复窗口

## 4. `recovery`

缓和节奏的卡，例如：

- 暂时休息
- 找朋友帮忙
- 调整选校策略
- 拆分任务

特点：

- 不等于纯奖励
- 常常是一项恢复，另一项小代价

## 5. `knowledge`

专门补知识的卡，例如：

- 为什么推荐信不能临时要
- 为什么代写 SOP 风险高
- GRE optional 的真实含义

特点：

- 教学意义高
- 数值波动可以较小

# 抽卡系统设计

每回合不是“直接随机抽一张”，而是走 4 个阶段。

## 第 1 步：检查强制卡

优先级最高：

- 当前 phase 的 milestone 到了
- 上一张 choice 触发了 follow-up
- 某项 stat 过低，触发 emergency 卡
- 某个 pending consequence 需要回收

如果命中，直接出卡，不进入随机池。

## 第 2 步：构造候选池

从数据库中过滤出满足条件的卡：

- phase 匹配
- route 匹配
- requirements 满足
- 不在 cooldown
- 没有违反 once_per_run
- 不和最近几张卡过度重复

## 第 3 步：对候选卡打分

每张候选卡都计算一个最终分数：

`finalScore = baseWeight × phaseFit × routeFit × difficultyFit × recoveryFit × noveltyFit × knowledgeFit × pacingFit × consequenceFit`

各项含义：

- `baseWeight`
  - 内容设计者手动给的基础权重
- `phaseFit`
  - 当前阶段适不适合出
- `routeFit`
  - 玩家路线是否匹配
- `difficultyFit`
  - 当前数值和压力值是否适配这张卡
- `recoveryFit`
  - 玩家太危险时，提高恢复卡权重
- `noveltyFit`
  - 避免类别、角色、文本功能重复
- `knowledgeFit`
  - 当前还没覆盖到的重要知识点加权
- `pacingFit`
  - 控制整体节奏，避免连续高压
- `consequenceFit`
  - 如果这张卡能承接前面埋下的选择，则加权

## 第 4 步：加权随机

不要直接选分数最高的卡，而是：

- 取分数前几名
- 做一次加权随机

这样：

- 每局有变化
- 但变化在可控范围内

# 导演层的难度控制

系统不能只看单张卡强不强，还要看“最近几张卡的组合”。

建议加 5 条硬规则：

## 1. 不允许连续两张 `crisis`

除非是特定 boss 段或结局段。

## 2. 某项主数值低于 25 时，未来 1 到 2 张内必须出现缓冲机会

例如：

- `energy < 25` 时提高 `recovery` 和低压 `dynamic` 卡权重
- `mentality < 25` 时降低高压社交/等待卡概率

## 3. 不允许连续三张都主要打击同一数值

比如连续三张都重伤 `energy`，会让体验很僵。

## 4. 里程碑卡的强度应该稳定，中间随机卡负责波动

主线推进卡不应承担过多随机惩罚，否则玩家会觉得“剧情杀”。

## 5. 必须有节奏曲线

建议是：

- 阶段初期：偏探索、偏教学
- 阶段中期：压力上升
- 阶段末尾：危机或结果结算
- 危机后：给恢复窗口

# 数值设计规则

你们现在的四维 `0-100` 可以保留，但需要统一标尺。

建议先定一个简单标准：

- 轻微影响：`5-10`
- 中等影响：`10-20`
- 强影响：`20-30`
- 极端影响：`30+`

然后给不同卡类型设上限：

- `milestone`
  - 通常只做中等波动
- `dynamic`
  - 轻到中等波动
- `crisis`
  - 可以强波动，但不能频繁
- `recovery`
  - 恢复一项，可能轻伤另一项
- `knowledge`
  - 数值变动最小

另外建议每张卡额外维护一组隐藏平衡参数：

- `impact_score`
- `variance_score`
- `recovery_score`
- `frustration_risk`
- `knowledge_priority`

这些值不直接展示，但对导演层选卡很有用。

# 教学目标如何嵌入卡牌系统

这不是纯娱乐游戏，所以抽卡目标不只是“让玩家活下去”，还要保证“这一局学到了完整知识链”。

每张卡建议加：

- `educational_tags`
  - 例如 `IELTS`, `SOP`, `Recommendation`, `Interview`
- `learning_goal`
  - 这张卡希望玩家理解什么
- `misconception_tag`
  - 容易犯的错是什么
- `guide_entry_id`
  - 对应知识库或 guide 页面

这样导演层可以补教学空白。

例如：

- 这局还没教到推荐信流程
- 玩家刚踩了“代写文书”的坑
- 下一张可以更倾向于出一个解释型卡或相关后果卡

# 推荐的运行流程

一局游戏建议按 phase 切分。

例如：

1. `prep`
   - 选路线、语言考试、早期准备
2. `application`
   - 选校、推荐信、文书、材料提交
3. `interview`
   - 模拟面试、正式面试、临场压力
4. `waiting`
   - 等结果、心态管理、补申/备选
5. `result`
   - offer / rejection / 延申结局

每个 phase 内：

- 先确保 1 到 2 张 milestone
- 其间插入若干 dynamic 卡
- 必要时插入 crisis 或 recovery

这样能兼顾结构感和随机性。

# 伪代码

下面是抽下一张卡的核心伪代码：

```ts
function drawNextCard(runState) {
  const forcedCard = findForcedCard(runState);
  if (forcedCard) return forcedCard;

  const candidates = allCards.filter(card =>
    matchesPhase(card, runState) &&
    matchesRoute(card, runState) &&
    meetsRequirements(card, runState) &&
    !isOnCooldown(card, runState) &&
    !violatesRepeatRules(card, runState) &&
    !alreadyBlocked(card, runState)
  );

  const scored = candidates.map(card => ({
    card,
    score:
      baseWeight(card) *
      phaseFit(card, runState) *
      routeFit(card, runState) *
      difficultyFit(card, runState) *
      recoveryFit(card, runState) *
      noveltyFit(card, runState) *
      knowledgeFit(card, runState) *
      pacingFit(card, runState) *
      consequenceFit(card, runState)
  }));

  const topPool = takeTopN(scored, 5);
  return weightedRandom(topPool);
}
```

# 平衡验证怎么做

这一步很重要，不然你们最后会靠手感调卡。

建议做两种验证：

## 1. 自动模拟

写一个本地 simulator，不接 UI，直接跑 1000 局。

观察：

- 平均局长
- 各阶段死亡率
- 死亡原因分布
- 四维均值和方差
- 不同路线胜率
- 教学标签覆盖率

## 2. 真实玩家埋点

记录：

- 哪些卡被抽到最多
- 哪些 choice 被选得最多
- 玩家通常死在哪个 phase
- 哪些卡导致流失或挫败感最高

这样数值调整就有依据。

# 结论

最终最推荐的方案是：

- 数据库存所有卡牌
- 卡牌分为 milestone / dynamic / crisis / recovery / knowledge
- 主线保证关键知识点出现
- 支线用导演算法受控随机抽取
- 用 `pressure + cooldown + repeat rules + recovery bias` 控制难度
- 用 `educational_tags` 保证教学目标
- 用 `run history + simulation` 做后续平衡

这套方案的优点是：

- 比当前 `gameStore` 写死分支更容易扩展
- 比纯随机更稳定
- 比纯线性更有重玩价值
- 很适合你们“教学导向”的类 Reigns 项目

下一步可以继续细化两件事：

1. 画出数据库 schema 草图
2. 把 `Director` 的输入输出和 TypeScript 接口先定义出来

如果继续做，建议下一步先做第 2 个，因为它会反过来决定数据库表结构到底需要存哪些字段。

# 开发方案

为了不把项目拖进长时间“先设计、后停滞”的状态，开发上采用分阶段迁移。

## 阶段 A：运行时架构拆分

目标：

- 不改可见玩法
- 不立刻接数据库
- 先把 `gameStore` 里的职责拆出来

要做的事：

- 提取 demo 卡牌数据到独立模块
- 新建 `repository`
- 新建 `director`
- 新建 `reducer`
- 新建运行时 `state` / `types`
- 让 `gameStore` 改为消费 runtime 层

完成标准：

- 当前 demo 还能跑
- 当前剧情分支和特殊事件还保持原样
- 后续数据库接入时不需要再大改 UI store

## 阶段 B：本地内容驱动

目标：

- 让内容和逻辑彻底分离
- 不再在 store 里硬编码卡牌

要做的事：

- 统一卡牌数据入口
- 把 special events 也纳入统一 card catalog
- 用 metadata 标注 `milestone / crisis / recovery / knowledge`
- 支持 `requirements / weight / cooldown / flags`

完成标准：

- 抽卡逻辑只依赖运行时状态和卡池
- 新增卡牌只改内容层

## 阶段 C：导演算法第一版

目标：

- 从“顺序抽卡”过渡到“受控随机”

要做的事：

- 加候选池筛选
- 加基础打分
- 加低血保护
- 加重复惩罚
- 加恢复窗口偏置

完成标准：

- milestone 继续稳定推进
- dynamic 卡开始受控随机
- 难度不再完全靠手写分支

## 阶段 D：数据库接入

目标：

- 使用 Supabase/Prisma 托管卡牌和 run 数据

要做的事：

- 设计 `cards / runs / run_card_history / balance_configs`
- 建 repository 的 remote adapter
- 从数据库加载 card catalog
- 记录每局历史

完成标准：

- 卡牌不再依赖本地常量
- 一局的选择轨迹可以被记录和分析

## 阶段 E：平衡与内容生产

目标：

- 让系统真的进入可迭代状态

要做的事：

- 加自动模拟脚本
- 看死亡率和知识覆盖率
- 扩充 phase 内容
- 建立数值标尺和内容模板

完成标准：

- 新卡可持续生产
- 抽卡和平衡有数据依据

## 当前立即执行的部分

现在先直接做阶段 A。

原因：

- 这是后续独立开发的必要地基
- 风险最低
- 不会马上把项目推进到“需要后端和数据库都准备完才能继续”的阻塞状态
